## B. Bugs and regressions (ranked)

1. **[High, Workers-only regression] Search quality.** `workers/d1/build-plugin.mjs` rewrites `MATCH … AGAINST` to `name LIKE '%term%' OR description LIKE '%term%'`. SQLite `LIKE` is case-insensitive for ASCII only and never accent-insensitive, and the whole query is one phrase. Verified locally against a product "Cámara de seguridad WiFi" (description "visión nocturna"): `camara` → 0 results, `CÁMARA` → 0, `Cámara` → 1; `funda celular` → 0 although "Funda de silicona para celular" exists; `vision nocturna` → 0, `visión` → 1. MySQL (utf8mb4 ci collation + boolean mode per-word prefixes) finds all of these, so this is a real regression versus the Node build. `%`/`_` in user input are also unescaped. Fix: a native batched search reader in `workers/d1/public-catalog-sql.mjs` (one `db.batch`, same projection as `catalogRead`) matching **each word** against an accent-folded lower-cased expression (nested `replace()` for áéíóúñü, or a stored `search_text` column added by migration), escaping `%`/`_`; wire it through the plugin's existing `@/db/queries` rewrite for `src/app/buscar/page.tsx`, and wrap it in `publicRead("search:v1:"+normalizedTerm)` so repeated terms share the 30 s data cache. Add fixtures with accents and multi-word names to `tests/workers/public-catalog.test.mjs`.

2. **[High] Open Graph fallback image returns a plain-text 404.** Home and category HTML emit `<meta property="og:image" content="https://productos.com.py/opengraph-image?…">` (verified locally), but `workers/d1/policy.mjs` `d1StagingRoute` allowlist does not include `/opengraph-image`, so WhatsApp/Facebook previews of the home page and every category page have no image. Product pages are fine (R2 image). Fix: allow `GET/HEAD ^/opengraph-image$` (and decide about `/feed.xml`, also blocked) in `d1StagingRoute`, then verify the `next/og` `ImageResponse` route actually renders in the Workers runtime (wasm deps); if it does not, commit a static 1200×630 PNG and point `openGraph.images` at it, or at an R2 asset. Verify live by fetching the URL after deploy.

3. **[Medium] Branded 404 is bypassed for any unknown path.** Any GET outside the allowlist (typos, uppercase slugs such as `/categoria/Tecnologia`, old Hostinger URLs, `/favoritos`, `/checkout`, `/cuenta`) returns `text/plain` "Feature not available in this isolated D1 catalog pilot." with status 404. Known-slug misses (`/producto/no-existe`) correctly render the styled `not-found.tsx`. Fix: for GET/HEAD unknown paths let the app render `not-found` (keep 405/403 for mutations and keep admin/actions blocked), or serve a branded static 404; drop the "pilot" wording from production.

4. **[Medium, latent] Stock-mode products expose a dead-end cart on Workers.** `add-to-cart.tsx` and `cart-sheet.tsx` are not gated by `catalogOnly`; a product with `sale_mode='stock'` (the import default when the column is absent, and editable via the allowlisted `saveProduct`) renders "Agregar al carrito" (verified locally); `add()` opens the cart sheet whose checkout link goes to `/checkout` → plain-text 404, and `sync()` calls blocked actions. The live catalogue is enquiry-mode so this is dormant today. Fix: in the Workers build treat `purchasable=false` when `catalogOnly` and show the enquiry CTA; do not mount `CartSheet`.

5. **[Medium] "También te puede interesar" never renders for an enquiry catalogue.** `relatedRead` joins `v.on_hand > 0` and filters `available > 0`; the Dropi import records on-hand 0 for enquiry items (docs/operations/dropi-catalog-rollout). Verified locally: product page has no related section, yet a `related` D1 batch runs on every cold product render (4 reader loads: settings, categories, product, related). The Node `getSameCategoryRelated` has the same restriction. Fix: for `saleMode !== 'stock'` drop the stock requirement (keep it for stock items); this both restores discovery and removes a wasted dependent D1 phase.

6. **[Low] SQLite BINARY collation differs from MySQL ci collations.** `ORDER BY p.name`, `GROUP BY p.brand`, `p.brand = ?` (brand filter) and the brands facet are case- and accent-sensitive on D1 (e.g. "tramontina" and "Tramontina" are two facets; names starting with Á sort after Z). Fix: `COLLATE NOCASE` where ASCII suffices, or normalise brand at import.

7. **[Low] Category render has an avoidable dependent phase.** `src/app/categoria/[slug]/page.tsx` awaits `getStoreSettings()` before the `Promise.all` of products+brands; locally the diagnostics show categories → settings → category/brands as sequential phases. Move `getStoreSettings()` into the `Promise.all`. Same idea on the product page: start `getRelatedProducts` together with settings/reviews (or skip it per item 5).

8. **[Low] Dead code:** `workers/d1/home-products.ts` and `workers/d1/latest-category-products.mjs` are only referenced by their own test since `latestRead` replaced them.

9. **[Low] `removeD1ProductImage` deletes the DB row but leaves the R2 objects** (webp boxes + jpeg) — storage leak over time; also does not verify the product exists (harmless).

10. **[Info] `categoryRead` would bind `NaN` if ever called with a non-numeric `page`** (`Math.max(1, NaN)`); pages guard it today. Add `Number.isSafeInteger` inside the reader.

## C. Caching and data safety (verified)

- Public projections are allowlisted columns; `dropi_url`, supplier costs, pending reviews, customer data never appear (fixture with private values confirmed absent in HTML).
- Hidden-price masking: variants carry `pricePyg: 0`, cards/pages show no price, metadata description omits price (verified).
- Publication: `is_active`, `published_at`, category `is_active` enforced in every reader (draft and hidden-category products 404 locally).
- Bypass: HTML cache requires anonymous `GET https` with `Accept: text/html`, no query, no cookie/authorization/RSC/action/range/conditional/no-cache headers; data cache requires no cookie/authorization/next-action/range/no-cache. Namespaces include version id and origin. Absolute expiry: data entries start the clock before D1; HTML `expiresAt = min(now+ttl, data expiry)`; hits recompute remaining TTL. Reader failure sets `failed` → HTML not cached (also covers `storeCategories()` fallback because the error is recorded before being swallowed). Hot cache clones values (`structuredClone`), bounded to 200, single-flight shared across requests.
- **Design concern [Medium]:** *any* `Cookie` header disables both caches. Today anonymous shoppers get no first-party cookie on Workers (analytics is off there: `cargarIntegraciones` short-circuits without `DATABASE_URL`, so panel integrations are never read on Workers and only `WHATSAPP_NUMBER`/ajustes apply; next-themes uses localStorage). Enabling GA4/Meta Pixel (`_ga`, `_fbp`) or Cloudflare bot cookies would silently cut hit rates to near zero for returning visitors. Recommendation: bypass only on the named session cookies (admin iron-session, customer session) and strip other cookies from the render request; add a test.
- **[Low]** data-cache keys include raw `brand`/`page` query values (unbounded Cache API cardinality; hot map is bounded). Cap brand length or hash keys.
- TTL stacking is correct: ≤30 s server data + ≤30 s Vinext full-prefetch = ≤60 s (constants in `public-cache-budget.mjs`; `staleTimes` supported by Vinext 1.1.0, confirmed in `dist/shims/navigation.js`).

## F. Performance (elapsed vs. billed CPU kept separate)

Local diagnostics (local D1, so durations are not network latency): home 5 reader loads in **one parallel phase** (settings, categories, featured catalog, catalog, latest); category 4 loads in **three sequential phases** (item 7); product 4 loads in **two phases** (product → related, item 5); search 2 loads plus 3 dependent drizzle phases (search → variants/images → holds/ratings), uncached and `force-dynamic`.

Suggestions, highest value first:
1. Fix search (B1) with a single batched, cached reader — biggest elapsed win per request on Workers.
2. Skip `related` for non-stock items (B5) and parallelise settings on the category page (B7) — each removes one edge→D1 round trip (~130–250 ms from GRU) on cold renders.
3. Cold homepage: the five parallel batches could be one `db.batch` under a `home:v1` key. This saves per-request overhead but not elapsed (they already overlap) and does **not** reduce D1 billed rows read. Most of the ~1 s cold home is render + one D1 phase + full HTML buffering before first byte on MISS; streaming-while-caching would need a redesign of how `x-catalog-expires-at` is finalised (store expiry conservatively as `now+30 s` since all data entries are ≤30 s fresh) — optional.
4. Cache-gate on named cookies only (C) — protects hit rate if analytics is ever enabled.
5. Prefetch: bounded and intent-only as designed; `touchstart` + 120 ms dwell can still prefetch on a long press without movement — acceptable. Each prefetch is a billed Worker request (CPU small; D1 rows only on data-cache miss).
6. Images: R2 pre-sized WebP with correct `srcset`/`sizes`, `immutable` caching, eager+`fetchpriority=high` for first cards — good. No change needed.
7. Billing framing: cache hits still invoke the Worker; D1 charges rows read/scanned, not queries; the 262-product catalogue makes all current scans small. Account figures in `docs/operations/cloudflare-usage-2026-10-10.md` (not re-verified against official pages: docs host blocked here).
