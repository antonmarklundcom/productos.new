# Offline encrypted Workers recovery bundles

Reviewed 24 October 2026. This implements a private **offline packaging and restore-preparation pipeline**, with synthetic tests. It does not capture production, establish provider consistency, create independent storage, import a database, prove login/decryption, or activate a backup schedule. No approved RPO, RTO, independent destination or retention is implied by the example.

## Commands and private inputs

Use Node 24 and existing dependencies; this tool itself uses only Node built-ins:

```text
node scripts/workers-recovery-bundle.mjs pack --config <absolute-private-config-path>
node scripts/workers-recovery-bundle.mjs verify --config <absolute-private-config-path>
node scripts/workers-recovery-bundle.mjs prepare-restore --config <absolute-private-config-path>
node --test tests/workers/recovery-bundle.test.mjs
```

Create the real JSON configuration outside this repository and OneDrive, using `workers-recovery-bundle.example.json` as a field guide. All filesystem paths must be absolute; artifact paths use relative `/` segments under sourceRoot. sourceRoot contains only an **already authorized, immutable capture**. Supply the exporter-recorded SHA-256 and byte size of each original file. Include separate matching schema/data exports, private runtime configuration, every R2 object and the capture certificate. Preserve the complete original export as an additional artifact where appropriate; the tool never rewrites SQL. R2 paths may be opaque inventory filenames; retain original object keys, MIME/custom metadata, object/version identifiers and their mapping in the private certificate or private-config artifact. All such metadata stays encrypted.

The certificate is an exporter-produced document recording the accepted consistency procedure and immutable source identity, capture/bookmark timestamps, Git revision, migration journal/hashes, table/index/trigger inventory, row counts, R2 inventory/hashes and actual cross-resource capture boundary. Its file hash is required in capture.certificateSha256. A write pause or immutable source must be deliberately authorized and implemented by a separate exporter/operator. The tool authenticates bytes and the supplied attestation; it **cannot prove that an exporter's consistency claims are true**. `consistencyAccepted` and `immutable` are required operator assertions, not provider receipts generated by this tool.

Policy requires an explicit owner approval reference, destination identity, independence evidence, positive integer RPO/RTO seconds and an owner-chosen retention description. `independentCopy:true` is an operator attestation of the selected failure boundary; local synthetic directories do not satisfy production independence. The tool does not test destination-provider independence. `automaticDeletion:false` is mandatory. No retention deletion, source removal, provider access, copy to another provider, credential discovery or scheduling occurs.

Supply exactly one key source: process-only `WORKERS_RECOVERY_KEY` with 64 hexadecimal characters (32 random bytes), or config.keyFile pointing to a private file containing that encoding. Never pass the key in arguments, commit it, print it, include it in reports, or store it beside the only recovery copy. Keep its independent vault recovery procedure outside the bundle. The private runtime config may include SESSION_SECRET because integration settings depend on that original secret; only explicit authorized exports should supply it. This tool never reads the running application's environment files or provider credentials.

## Storage and encryption contract

privateRoot must already exist and be private. bundlePath must be a new direct-child-or-descendant target with an existing canonical parent under privateRoot. Source and target paths must resolve canonically; junctions/symlinks and escapes are rejected. Repo and OneDrive destinations are rejected. A separate root outside these rejected locations is not proof of appropriate OS permissions or independent storage: the operator must provision restrictive Windows ACLs or equivalent permissions before use. POSIX files/directories request 0600/0700. Restrict config/key/source roots too.

Each artifact streams through SHA-256 and AES-256-GCM to a random opaque filename. Every artifact and the manifest has a distinct random 96-bit IV and 128-bit authentication tag. The authenticated additional data binds format, bundle identifier and artifact identifier; the sealed manifest binds paths, roles, expected hashes/sizes, policy and capture metadata. Only format, random bundle identifier and encrypted file count/lengths are visible outside encryption. The 16 MiB manifest limit bounds parsing; large object bytes are streamed, not accumulated in memory. Each bundle must be treated as immutable after successful packing. File access assumes a trusted operator and no concurrent modification by another process with the same filesystem permissions.

`verify` authenticates the sealed manifest, validates paths/roles/policy/certificate linkage, checks unique IVs and decrypts every artifact to a discard sink while validating its original hash and size. Ciphertext/header/manifest tampering, missing objects, wrong keys and changed source hashes fail closed. Success summaries contain only status, count and scope. CLI errors use a fixed sanitized message; investigate private inputs privately rather than adding secret-bearing diagnostics to shared logs.

`prepare-restore` requires a **new**, explicitly private isolated target with outgoing integrations disabled and production traffic false. It verifies the complete bundle before creating the plaintext target, then decrypts each artifact and rechecks integrity. It refuses an existing target and overlap with the bundle. It never invokes SQL or Wrangler. The prepared private files are still sensitive; do not add them to Git or reports. A failed pack can leave a partial encrypted directory; a failure during preparation can leave a private partial plaintext directory. The tool never deletes either automatically. Retain/inspect under the owner's policy and choose a new target for a retry; do not label a partial output verified. Do not run concurrent writers against these roots.

## Isolated application restore and acceptance

Continue with the reviewed [Workers recovery runbook](workers-recovery.md): create a new isolated D1/R2 target only after approval, no production bindings/domains/cron/outgoing integrations; verify target IDs before import. Import the matching captured schema before data, preserving original files and deferred foreign-key handling. Validate complete table/index/trigger inventory, counts, foreign keys, money/order/counter invariants and media object hashes/metadata. Keep encrypted settings and the original SESSION_SECRET together privately; exercise actual owner login/session revocation and settings decryption with outgoing integrations disabled. Record actual recoverable timestamp and elapsed time against approved RPO/RTO. Cutover requires separate owner acceptance.

The existing `verify-workers-recovery.mjs` supplies a synthetic local Wrangler/Miniflare schema-first rehearsal; its generated fixture is separate from these packaging tests. A passing packaging test or synthetic rehearsal does not establish production-derived restore acceptance. Keep production recovery status pending until real authorized exports, an independent copy and isolated application acceptance have evidence.
