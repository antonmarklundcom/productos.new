# Workers Spanish catalogue search

23 October 2026. The Workers public search reader uses `catalog-search-sql.mjs`; the retained MySQL reader keeps its own full-text behavior. Only published active products in active categories match. Page/count predicates are identical, selection order is deterministic and selected IDs are hydrated in that order.

## Matching contract

Input is NFC-normalized, lowercased in Spanish, trimmed and whitespace-collapsed. Accented Spanish vowels and ü fold to their unaccented equivalents; ñ remains distinct from n. Database expressions fold precomposed Spanish vowel accents, Ü and Ñ with SQLite replace/lower. Stored decomposed Unicode sequences are not normalized by SQLite; normalize imported catalogue text separately if that case becomes relevant. This is Spanish matching, not general Unicode collation.

All distinct whitespace-separated tokens must appear as substrings somewhere in name, brand or description; tokens may span fields and occur in any order. This is neither stemming nor whole-word matching: a token can match within a longer word. `%`, `_` and `!` are literal characters, safely escaped for LIKE, and values are always bound parameters. Punctuation is otherwise retained literally.

Ranking prioritizes exact folded name, then folded name prefix of the whole phrase, exact brand of the whole phrase, all tokens in name, then other matches. Folded name and product ID resolve ties. Queries under 2 characters, above 160 characters or above 12 distinct tokens return no matches. Page size defaults to40 and is clamped1–60. This local fixture contract is not an owner relevance study.

## Repeatable local measurement

Run `node scripts/profile-workers-search.mjs [output.json]`. It creates only synthetic in-memory SQLite databases at262,1000 and10000 products. No provider binding, catalogue export, credential or installation is used. Five fixed terms exercise accents, reordered words, ñ, literal wildcard punctuation and a normal match. Two warmups and seven measured rounds alternate old/new/repeated-folding order. The JSON records counts, first IDs, per-round wall times, medians and EXPLAIN QUERY PLAN for selection/count. It does not import test files or register tests.

The baseline reproduces the former Workers source transform: a whole-phrase LIKE in name/description; if that count is zero, retry name/brand. The old path does not escape LIKE wildcards. The new path uses the actual current `searchPlan`, including its token folding/ranking and count. A third measured path disables materialization through the internal third searchPlan argument to compare the same matching/ranking semantics using repeated folding expressions. Every fixture asserts exact selected-row/order/count parity before reporting. The default uses a MATERIALIZED CTE of visible candidates, computing each folded field once per candidate per statement; selection and count remain separate statements. Both include SQL preparation, SQLite execution and result materialization; hydration and network are excluded. The small synthetic schema has primary keys and a category index, not every production table/index/data distribution. Query-plan output for old counts describes both possible predicate branches, even when fallback is not taken. Treat times as mechanism comparison rather than visitor latency or D1 billing.

The 23 October result in `completion/SEARCH-PROFILE.json` shows a correctness/cost tradeoff: at10000 products, old queries took roughly4–6ms and materialized new queries106–199ms; at262, new queries roughly3.6–4.0ms. Two-token CTE queries took106–110ms versus repeated-folding145–173ms in the same run. The single-token Niño fixture regressed199ms versus187ms; this is not a universal optimization. Concurrent local work and runtime variability limit exact ratios. Unaccented/reordered café searches changed from zero matches to3531 at10000, while literal wildcard matching removed false positives2349→1174. New code is not faster in this benchmark. Materialization avoids repeated folding per token, but it still folds visible rows twice across selection/count and scans/ranks substrings. This cost remains material at10000 products; normalized search columns/index design or FTS with reviewed literal/substring semantics is follow-up work. Nested replace expressions, substring scans, count and ranking add work; neither ordinary name indexes nor this measurement establish an FTS optimization. A production-like approved measurement and relevance decisions should precede larger catalogue optimization.

## Diagnostics and limits

`WORKERS_PUBLIC_DIAGNOSTICS=true` is an explicit preview/local profiling option. It buffers the complete response to observe late readers; do not enable it for normal shoppers. Its headers contain numeric batch/count/timing metadata and allowlisted reader names, not SQL, parameters, search terms or actor identities. The D1 batch/service/rows-read counters cover only instrumented native public catalogue SQL helpers. Drizzle settings reads, other layout/legacy queries and authentication are outside that counter coverage. Do not treat these as total request SQL or D1 billing. Response-header and full-body timings cover the overall wrapped response, so residual time is unattributed; it is not proven rendering or CPU. These scopes cannot be subtracted to identify browser rendering or CPU. Public cache hits may execute no D1 queries; concurrent flights can attribute load to the request that started it. Browser rendering/network and real device acceptance remain separate measurements.
