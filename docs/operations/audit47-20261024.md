## Import and publication procedure

Staff can review CSV/Excel, inspect duplicate warnings and confirm the reviewed file. Native upload size is at most 800 KB; direct import accepts at most 500 products and commits atomic five-product batches. Earlier direct batches can become public before a later batch fails. Stock purchasing remains disabled; use enquiry/showcase products.

The server persists a private normalized plan once, including actor/file/options identity and product revision baselines. Subsequent batches use that plan and targeted checks rather than rebuilding the whole catalogue plan. Costs/file contents stay on the server. Audit events contain allowlisted field names, not supplier values or raw files.

The optional **Preparar y publicar** mode prepares private checkpoints without changing public products. It accepts at most 50 products, 250 variants and a conservative 900-statement budget; complex files can require smaller splits. After all chunks prepare, review the summary and use **Publicar planilla completa**. Final publication validates existing revisions/new-slug absence, category identity, SKU ownership and R2 references, then writes the whole file, audit, receipt, checkpoint and publication status in one D1 batch. Revision guards run before product writes. An interrupted preparation publishes nothing. Conflicts require renewed review; do not bypass the guard.

Existing hidden products/variants retain visibility unless the separate **Reactivar productos y variantes ocultos** option is reviewed and enabled. File identity includes overwrite/reactivation/staging options. Default direct imports retain the previous v1 server hash; legacy browser identities resume only for the same file/stock option with reactivation and staging off.

After a lost acknowledgement or reload, choose the same file/options and review again. The browser keeps only a digest/random ID in session storage. Confirmed receipts replay without duplicate writes or changed original summary counts. Legacy partially committed imports keep their existing receipts. A different actor/file/options cannot reuse the ID. **Nueva importación** deliberately abandons that browser identity; use it only after reconciling an uncertain operation. No automatic plan/receipt/audit expiry is enabled.

Implementation: [staging](../../workers/d1/catalog-staging.ts), [atomic writer](../../workers/d1/catalog-import-write.ts), [durability contracts](../../workers/d1/catalog-durability.ts). This section supersedes the 23 October statement that whole-file staging was absent in [the earlier durability note](catalog-durability.md). The normal retained Next/MySQL import still has no native D1 receipt guarantee.

## Bulk changes, revisions and roles

Staff can select at most 50 products for native show/hide or move to an active category. Each row carries its displayed revision. Stale/missing records are listed as conflicts; accepted records commit with audit and an operation receipt. A race after validation aborts the atomic batch. Repeating an uncertain request uses the same operation ID.

Duplication is staff-only and revision-guarded. The deterministic copy is unpublished/inactive, not featured, with stock zero and no copied images or supplier offers; a legacy stock product becomes enquiry. Receipt replay returns the same copy. Bulk price adjustment, stock adjustment, checkout and payment actions remain disabled on the catalogue runtime. Owner-only product CSV export remains filtered, bounded, explicitly reports truncation and escapes spreadsheet formulas; private fields follow its allowlist.

Product, variant, supplier and gallery panels coordinate revisions. Dirty drafts are preserved during sibling saves and conflicts; a new server revision is not silently accepted over an old dirty draft. Reconcile/reload before saving a real second-editor conflict. History remains private and bounded; do not delete history or receipts to resolve an error.

Implementation: [native bulk](../../workers/d1/native-bulk.ts), [capabilities](../../src/lib/catalog-policy.ts), [action guards](../../src/lib/admin-guard.ts).

## Images, gallery undo and integrity reports

Product images require staff; category-photo upload requires owner. Prepared images are validated as WebP/JPEG bytes and expected dimensions, at most 1200 pixels on the longest edge and 800 KB total prepared payload. Uploads bind operation ID, actor, draft revision and file hashes, reserve the identity before R2 writes and finalize the receipt with the D1 reference. Retry the same operation after uncertainty. A changed draft cannot reuse its receipt.

R2 and D1 do not share a transaction. Immutable object names and idempotent uploads avoid replacing unrelated bytes. Never delete uploaded bytes merely because the response was lost. Gallery order/alt/removal/restore use revision guards and receipts. Removal creates a private tombstone with a 24-hour undo window; restoration is actor/product-bound and single-use. Removal/expiry does **not** delete R2 bytes, and no automatic garbage collection is enabled.

```text
node scripts/workers-media-integrity.mjs <absolute-path-to-authorized-inventory.json>
```

The [integrity reporter](../../scripts/workers-media-integrity.mjs) consumes complete supplied reference/object inventories; it does not fetch production inventories or delete anything. It reports missing/incomplete/mismatched objects and candidate orphans, protecting recent, pending or ambiguous objects with a default 24-hour grace. Candidate status is not permission to delete. Preserve unique media and rollback references.

Implementation: [upload writer](../../workers/d1/gallery-write.ts), [gallery receipts/undo](../../workers/d1/gallery-mutations.ts), [category images](../../workers/d1/category-image.ts).

## Public cache, search and health

The accepted freshness budget remains 30 seconds of public DTO reuse plus 30 seconds of browser full-prefetch reuse. HTML expiry is capped by its underlying data expiry, preventing another stacked cache interval. Private/cookie/auth/action requests bypass shared cache. A database failure discovered while buffering makes the response private/503 and prevents a cache write. Safe public GET/HEAD indexing policy matches; admin, preview and failures remain protected. Emergency global invalidation requires a separately accepted procedure.

Configuration remains explicit: `WORKERS_PUBLIC_CACHE_SECONDS` accepts integer 30–300 (otherwise off); DTO reuse is capped at 30 seconds. Production indexability requires `WORKERS_PRODUCTION_READY=true` and matching HTTPS `NEXT_PUBLIC_SITE_URL`; a workers.dev/invalid origin is insufficient. `CF_VERSION_METADATA.id` namespaces cache generations. `WORKERS_PUBLIC_DIAGNOSTICS=true` is preview/local profiling only: it buffers responses and emits bounded numeric diagnostics. Keep secret values out of documents and logs.

Search uses migration-maintained normalized fields while preserving Spanish accent folding, distinct ñ, literal wildcard/substrings, token ranking and deterministic ties. Search accepts 2–160 characters and at most 12 distinct tokens; page size is 1–60, default 40. Suggestions accept 2–80 characters and return at most six public items. Recently viewed hydration accepts at most eight validated slugs and rechecks public visibility/price permission.

Anonymous safe query reuse is version/origin-bound. Per-isolate bounds are 200 hot entries, 32 flights, and a 30-second cold-search window of at most 256 loads/64 distinct keys. These are local resource bounds, not a global rate-limit guarantee. Cache errors are sampled at the first and every 100th error using fixed numeric categories, without URLs, search terms, actors or secrets. See [cache reuse](../../workers/d1/public-data-cache.mjs), [metrics](../../workers/d1/cache-metrics.mjs) and [normalized search](../../workers/d1/search-normalization.mjs). The [older search profile note](workers-search.md) describes the prior folding baseline; rerun the current profiler for current comparisons.

`GET /health?live=1` (or `/api/health?live=1`) is liveness without a DB query. Ordinary health performs `SELECT 1`, returns structured 503 when unavailable, and uses no-store. `?details=1` deliberately requests catalogue counts; it returns only public aggregate catalogue totals on explicit request. No record/private-field payload is returned. Health JSON does not prove admin login, R2 integrity, recovery or payment availability. See [endpoint implementation](../../workers/d1/public-endpoints.mjs).

## Recovery tooling and remaining owner decisions

Existing `pnpm test:workers-recovery` rehearses synthetic local D1/R2/private-setting recovery. The new [offline bundle tool](../../scripts/workers-recovery-bundle.mjs) packages already captured artifacts; it does not contact Cloudflare, capture a live snapshot, execute SQL, restore a provider binding or establish production recovery.

```text
node scripts/workers-recovery-bundle.mjs pack --config <absolute-private-config.json>
node scripts/workers-recovery-bundle.mjs verify --config <absolute-private-config.json>
node scripts/workers-recovery-bundle.mjs prepare-restore --config <absolute-private-config.json>
```

Keep config, source exports, encrypted bundle, key and any prepared plaintext outside Git, project folders, reports and OneDrive. Configure exactly one key source: private key file or process-only `WORKERS_RECOVERY_KEY`; never paste the value into a command/report. The tool authenticates AES-256-GCM artifacts/manifest and checks declared SHA256/size. It refuses overlapping/existing restore destinations and requires a new private isolated target with integrations disabled and no production traffic.

Before real use the owner must select and explicitly approve an independent destination, RPO, RTO, retention and consistency procedure. The private manifest requires owner approval evidence, independent-copy evidence, immutable/accepted capture and a hashed capture certificate. These declarations are not independent proof that a changing production D1/R2 export is consistent. Required artifact classes include D1 schema/data, private configuration and the capture certificate; include all referenced R2 bytes with inventory/hashes.

No production-derived capture, independent copy or production restore has been demonstrated. Provider support/restore points, actual application login/settings decryption, complete media comparison and measured recovery time remain pending. No live schedule, automatic retention deletion or production cutover is enabled. Preserve receipt/audit replay when choosing retention. Follow [the recovery runbook](workers-recovery.md) for separately authorized capture and isolated application restore; accepting an offline bundle is not accepting recovery.
